## 디자인 2b

> **고딕 볼드형** — 초대형 블랙 고딕 표제, 냉회색 지면, 에디터 픽만 검정 띠
> 60 냉회색 지면 · 30 초대형 먹 활자 · 10 시안

색은 전부 `app/tokens.css` 한 곳에 있고, 컴포넌트는 리터럴 색을 쓰지 않는다.

|---|---|---|

| 표제·이름 | `#0c0c0c` | `--ink` |
| 부제 | `#33383a` | `--sub` |

서체는 표제 **Black Han Sans**(400 한 종), 본문 **Noto Sans KR** — `next/font/google`.
2b 의 위계는 색이 아니라 **굵기**로 만들어지므로, 괘선은 검정 한 색에 두께만 4px / 1px 두 값이다.

기획안 §8 의 "Pretendard 서빙 방식 미결정"은 디자인이 이 둘을 지정하면서 정리됐다.

### 구현한 화면

디자인의 홈 아트보드를 그대로 옮겼다 — 마스트헤드(제호 + 가제 + 카테고리 + 로그인),
굵은/가는 이중 괘선, 리드 기사(사진 좌·표제 우), 순번 붙은 카드 열,
에디터 픽 검정 띠, "이번 달에 쓴 사람들", 푸터.

1440px 고정이던 원본을 유동 레이아웃으로 옮겼다. 디자인 값이 상한이 된다
(여백 100px, 카드 280px, 간격 40px).

## 설치

```bash
npm install
cp .env.example .env.local   # 값을 채운다
npm run dev
```

### Supabase 준비

1. Supabase 프로젝트를 만들고 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY` 를 `.env.local` 에 넣는다.
2. SQL Editor 에서 `supabase/migrations/0001_init.sql` 을 실행한다.
3. **Authentication → Users → Add user** 로 관리자 계정을 하나 만든다.
4. 생성된 UUID 를 `supabase/seed.sql` 에 넣고 실행한 뒤, 같은 UUID 를
   `.env.local` 의 `ADMIN_AUTHOR_ID` 에 넣는다.

3~4번이 필요한 이유: `posts.author_id` 는 not null 이고 `profiles → auth.users` 를
참조한다. M1 은 인증이 없지만 auth 유저가 0명이면 글을 한 건도 삽입할 수 없다.
기획안 M1 체크리스트에 빠져 있던 단계다. 여기서 만든 계정은 M2 에서 매직링크가
붙으면 그대로 정상 로그인 계정이 되므로 버리는 작업이 아니다.

### `/write` 접근

M1 은 `ADMIN_PASSWORD` 환경변수 하나로 막는다(기획안 §6 M1).
입력하면 httpOnly 쿠키가 2주간 유지된다. M2 에서 Supabase Auth 세션으로 교체되며,
그때 `lib/adminGate.ts` 는 삭제된다.

## 디자인에서 판단이 필요했던 곳

**썸네일이 없는 카드.** 디자인의 모든 카드에는 사진이 있지만, 기획안 §1 은
썸네일 없이도 카드가 성립할 것을 M1 의 전제 조건으로 못박는다. 2b 의 30% 는
색면이 아니라 "초대형 먹 활자"이므로, 사진이 없는 카드는 회색 자리를 비워두는
대신 표제를 한 단계 키워 그 자리를 활자로 채운다. 디자인의 논리를 그대로 따른
것이고, 덕분에 AI 썸네일(M4)이 영영 안 붙어도 홈이 성립한다.

**사진 자리의 12px 안여백.** 목업에서 "가로 3:2" 같은 비율 주석을 얹기 위한
공간이라 옮기지 않았다. 그대로 두면 실제 사진 둘레에 회색 액자가 남는다.

**비율.** 목업의 사진 상자는 라벨과 실제 크기가 어긋난다(리드는 "3:2" 라벨에
740×416 ≈ 16:9). 저장된 `thumbnail_ratio` 로 `aspect-ratio` 를 잡았다 — 비율을
값으로 저장하는 이유가 §3.2 에 적힌 그대로이기 때문이다. 에디터 픽 띠 안의 사진만
저장값과 무관하게 3:1 로 자른다. 띠 고유의 판형이다.

**글 상세 화면.** 기획안 §8 이 미착수로 남긴 부분이다. 홈의 규칙(초대형 고딕 표제,
먹 괘선, 시안은 카테고리와 인터랙션에만)을 옮겨 구성했다. 사진은 본문 단과 같은
폭으로 묶었다 — 지면 전체 폭으로 펼치면 3:2 사진이 800px 넘게 자라 본문을 압도한다.

**마스트헤드의 검색·북마크 아이콘.** 디자인에 있어 그대로 두었지만 아직 아무
기능에도 연결돼 있지 않다. 눌러도 반응하지 않는 UI 이므로 M2 에서 기능을 붙이거나,
그전에 빼는 편이 나을 수 있다.

**푸터의 이용약관·개인정보.** 디자인에도 링크가 아닌 글자로 놓여 있고, 실제 법적
의무는 가입 기능이 붙는 M2 부터 생긴다(§6 M2). 문서가 생길 때까지 링크를 걸지 않았다.

**카테고리 라벨.** 디자인 표기를 따라 영문 대문자다 (ESSAY / PLACE / LOVE / LIFE /
EDITOR'S PICK). enum 값은 기획안 §3.1 그대로 `essay`/`place`/`love`/`life`/`pick`.

## 기획안에서 바꾼 것

**1. `likes` 에 anon insert 정책을 만들지 않았다.**
기획안 §3.2 는 비로그인 좋아요를 위해 쿠키 UUID 를 `actor_key` 에 넣자고 하지만,
§5.3 이 말한 대로 anon 키는 클라이언트에 노출된다. 그 상태로 insert 를 열면
누구나 `actor_key` 를 난수로 바꿔가며 좋아요를 무한 삽입할 수 있다.
마이그레이션의 RLS 정책은 **로그인 사용자만** 다루고, 비로그인 경로는 M3 에서
서버 액션(service role) 전용으로 붙인다.

**2. 카테고리 표시 이름을 `lib/categories.ts` 로 뺐다.**
스키마는 기획안대로 Postgres enum 이지만, enum 은 변경에 마이그레이션이 필요하고
카테고리는 매거진에서 가장 자주 바뀌는 축이다(§8 도 인정).

**3. `published_at` 을 DB 트리거로 박는다.**
애플리케이션이 잊어도 `posts_feed_idx` 가 비지 않도록 보장한다.

**4. 댓글 카운터 트리거가 UPDATE 도 처리한다.**
댓글은 소프트 삭제라(§3.2) INSERT/DELETE 만으로는 `deleted_at` 이 채워질 때
카운터가 내려가지 않는다.

**5. "이번 달에 쓴 사람들"을 M1 에 넣었다.**
기획안은 M2-1 로 잡았지만 디자인 홈에 있고, 이번 달 글만 받아 JS 에서 집계하면
되는 수준이라 먼저 만들었다. 필자 페이지 `/u/[handle]` 링크는 M2-1 이라 아직 없다.

**6. 컬럼 단위 GRANT 를 추가했다 (M2).**
1차 마이그레이션의 RLS 정책만으로는 **가입한 사람이 자기 profile 에
`is_admin = true` 를 써넣을 수 있었다.** RLS 는 어느 *행*을 건드릴지만 정하지,
그 행의 어느 *칸*을 건드릴지는 정하지 않기 때문이다. `is_admin()` 이 true 가 되면
`posts_update_own` 이 관리자에게 남의 글 수정을 허용하므로, 누구나 모든 글을
고치고 내릴 수 있게 된다. 가입이 열리는 순간 실제 권한 상승 경로다.
`revoke insert, update … grant (컬럼 목록)` 으로 막았고, 같은 방식으로
`like_count` 직접 조작과 댓글의 `post_id` 변경도 막았다.
`scripts/rls-test.mjs` 가 이 세 가지를 검사한다.

**7. 마스트헤드의 로그인 표시를 클라이언트에서 읽는다.**
서버에서 `cookies()` 를 읽으면 이 헤더를 쓰는 **모든 페이지가 동적 렌더링이 되어
ISR 이 사라진다.** 캐시된 지면에 개인 상태를 섞지 않는다는 §2.3 의 원칙이
좋아요·댓글뿐 아니라 로그인 표시에도 그대로 적용된다.
