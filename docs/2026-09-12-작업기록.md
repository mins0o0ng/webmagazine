## 2. `SUPABASE_DATABASE_URL` 다섯 번 실패 — 원인과 오진

실행 1~5 가 전부 `password authentication failed` 로 죽었다. 사용자명도
호스트도 맞았다.

### 내가 틀린 조언을 했다

"특수문자 없는 비밀번호로 재설정하세요" 라고 안내했는데, **Supabase 는
데이터베이스 비밀번호에 특수문자를 요구한다.** 애초에 따를 수 없는 조언이었다.
대안으로 `%40` 을 손으로 적으라고 시키는 것도 반드시 어딘가 틀리는 절차다.

### 왜 URL 이 깨지는가

Supabase 가 요구하는 특수문자가 전부 URL 구분자다.

| 글자 | URL 에서의 뜻 |
|---|---|
| `@` | 사용자정보와 호스트의 경계 |
| `:` | 포트 구분자 |
| `/` | 경로 시작 |
| `#` | 프래그먼트 시작 |
| `?` | 질의문자열 시작 |

`postgresql://postgres.ref:p@ss@host:5432/postgres` 를 파서는
"호스트가 `ss@host`" 로 읽는다.

### 고친 방법 — 비밀번호를 URL 밖으로

```
SUPABASE_DATABASE_URL   대시보드에서 복사한 그대로. [YOUR-PASSWORD] 그대로 둔다.
SUPABASE_DB_PASSWORD    원문. 인코딩하지 않는다.
```

`scripts/db-url.mjs` 가 한 곳에서 합치고 **한 번만** 인코딩한다. 사람이 `%40` 을
적을 일이 없다.

`p@ss:w/rd#1! "quo" ~-_.+&=%` 같은 비밀번호로 왕복 테스트를 돌려
`pg` 가 원문 그대로 복원하는 것을 확인했다. 이미 인코딩된 URL 을 다시 넣어도
이중 인코딩되지 않는다(멱등).

### 진짜 원인은 따로 있었다 — 우연히 잡혔다

새 방식을 넣고 돌린 실행 6 이 이상했다. **`psql` 은 붙었는데 `db:migrate` 만
거부당했다.**

```
CREATE FUNCTION
psql:supabase/check_rls.sql:135: ERROR:  column "can_write" ... does not exist
```

`psql` 이 실제 DB 에 붙어 SQL 을 돌리고 있었다. 둘의 차이는 하나뿐이었다 —
**job 의 `env:` 블록은 `$GITHUB_ENV` 로 나중에 넣은 값을 덮어쓴다.**
`psql` 은 원본 secret 을, `db:migrate` 는 내가 조립한 값을 받았다.

즉 **`SUPABASE_DATABASE_URL` 은 처음부터 맞았고, `SUPABASE_DB_PASSWORD` 에
틀린 값이 들어 있었다.** 내 버그가 원인을 증명한 셈이다.

두 가지를 고쳤다.

1. **우선순위를 뒤집었다.** 비밀번호 자리가 비어 있거나 `[YOUR-PASSWORD]` 일
   때만 `SUPABASE_DB_PASSWORD` 로 채운다. 이미 완성된 URL 에 덮어쓰면 멀쩡히
   붙던 접속이 조용히 깨진다. 채워 넣기는 빈칸일 때만 하는 일이다.
2. **job `env` 에서 `DATABASE_URL` 이라는 이름을 쓰지 않는다.**
   `SUPABASE_DATABASE_URL` 로 받아 조립한 것만 `DATABASE_URL` 로 내보낸다.

## 3. SQL Editor 에 손으로 붙여넣는 방식이 왜 계속 어긋났나

사용자가 두 파일을 실행하고 "성공했다" 고 했는데 확인 질의는 4개 다 `false`
였다. **SQL Editor 는 파일 전체를 한 트랜잭션으로 돌린다.** 한 문장이라도
실패하면 파일 전체가 롤백되고, 화면상으로는 성공처럼 보일 수 있다.

실행기가 붙자 DB 의 실제 상태가 한 번에 나왔다.

```
이미 적용됨: init · auth · lock_anon · notion
안 됨:       contrib · engage
```

`notion.sql` 은 들어가 있었다. 사람의 기억이 아니라 DB 에 물어봐야 알 수 있는
종류의 사실이다.

**워크플로에 `--adopt` 를 상시로 붙였다.** 손으로 만든 DB 라 기록이 비어 있는데,
그대로 돌리면 실행기가 "`--adopt` 를 쓰세요" 라고 안내만 하고 끝난다. 그 왕복이
바로 이 워크플로가 없애려던 것이다. 없는 것을 있다고 기록하는 경로는 없다 —
각 파일 첫 줄의 `-- applied-if:` 질의가 `true` 일 때만 건너뛴다.

**PostgREST 캐시도 깨운다.** DDL 직후 PostgREST 는 캐시된 스키마를 들고 있어서
`db:admin` 과 `test:rls` 가 "`can_write` 가 schema cache 에 없다" 로 죽었다.
마이그레이션 끝에 `notify pgrst, 'reload schema'` 를 보낸다.

## 5. 노션 동기화 점검 — 구멍 둘을 먼저 막았다

M2-4 는 **아직 한 번도 돈 적이 없다.** 도는 순간 만날 가능성이 높은 곳을
먼저 봤다.

### 스키마는 맞다

노션 「웹매거진 원고」의 속성이 코드가 기대하는 것과 전부 일치한다 —
제목(title) · 부제(text) · 상태(select) · 카테고리(select) · 썸네일(url) ·
썸네일 비율(select) · 필자 핸들(text) · 동기화(text).

상태 네 값 `작성중 / 초안 / 발행 / 숨김` 도 `STATUS` 맵과 맞고,
`숨김` → `posts.status = 'hidden'` 은 DB enum 에 있는 값이다.

### 구멍 1 — 설정 실수 한 번에 지면이 통째로 내려간다

동기화 끝에 "노션에서 사라진 행은 숨김 처리" 하는 청소 단계가 있다. 그런데
**"노션이 비었다" 와 "노션을 못 읽었다" 가 여기서 구분되지 않았다.**

후자가 훨씬 흔하다. 통합 연결이 끊기거나, `NOTION_DATABASE_ID` 가 엉뚱한 DB 를
가리키거나, 권한이 바뀌면 **질의는 성공하고 결과만 0행으로 온다.** 그대로 두면
발행된 글이 전부 내려간다.

→ 0행이면 청소를 건너뛰고 왜 건너뛰었는지 보고한다.

### 구멍 2 — 목록이 잘리면 나머지가 전부 사라진 것이 된다

`queryDatabase` 가 1000행에서 조용히 `break` 했다. 부분 목록이 밖으로 나가면
그 뒤의 글이 전부 청소 대상이 된다.

→ 잘릴 상황이면 던진다. 부분 목록을 내보내지 않는다.

## 8. 남은 판단 하나

`SUPABASE_DB_PASSWORD` secret 에는 지금 **틀린 값**이 들어 있다. 지금은 URL 이
완성돼 있어서 무시되지만, 나중에 누군가 URL 을 `[YOUR-PASSWORD]` 형태로 바꾸면
그 순간 틀린 비밀번호가 쓰인다. **지우거나 올바른 값으로 고쳐 두는 편이 낫다.**
