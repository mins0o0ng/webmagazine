## 0. 먼저 정리된 오해 두 가지

**"글을 노션에서 가져온다."** 아니다. `notion` 이라는 단어는 레포 전체에서
`supabase/seed_posts.sql:3` 의 주석 한 줄뿐이다.

```sql
-- 출처: Notion 페이지 "♥️ 산책자" (2026-07-16 기준)
```

원고 19편을 노션에서 **한 번 긁어와 INSERT 문으로 바꾼 기록**이고, 런타임에 노션 API 를
부르는 코드는 없다. 패키지도, 토큰도 없다. 글은 전부 Postgres `posts` 테이블에서 나오고
`/write` 에서 쓴 글이 곧바로 거기 들어간다. **DB 가 원본이다.**

**"글 입력·편집 기능이 없다."** 있다. M1 부터 `components/PostEditor.tsx`(마크다운
textarea + 미리보기), `app/write/`(새 글 · 수정), `app/write/actions.ts`(발행 · 임시저장)
가 있었다. 보이지 않았던 이유는 `ADMIN_PASSWORD` 자물쇠 뒤에 있었고 Supabase 연결을
한 번도 세워본 적이 없어서다.

## 1. M2-1 — 타인 기고 (초대제)

### 결정: 심사제가 아니라 초대제

M2 까지의 `posts` 정책은 `author_id = auth.uid()` 만 본다. 그 상태로 `/write` 를
세션 인증으로 열면 **가입한 누구나 즉시 `status = 'published'` 로 홈 1면에 올릴 수 있다.**
편집권이 없는 매거진은 게시판이고, 스팸글 한 건에 매체 전체의 신뢰가 걸린다.

선택지는 셋이었다.

| | 방식 | 비용 |
|---|---|---|
| (a) | 누구나 발행 | 스키마 변경 0. 대신 신뢰가 글 하나에 걸림 |
| (b) | 글마다 심사 큐 (`draft → review → published`) | 글마다 편집자가 붙어야 함 |
| (c) | **사람마다 한 번 초대** | 사람마다 한 번만 붙으면 됨 ← 채택 |

**(c) 를 골랐다.** 이 규모에서 지속 가능한 쪽이 후자다. 발행량이 늘어 초대만으로
품질이 안 잡히면 그때 `post_status` 에 `'review'` 를 더하면 된다. 스키마는 그 방향으로
열려 있다.

### 스키마 (`20260907000000_contrib.sql`)

```sql
alter table profiles add column if not exists can_write boolean not null default false;
update profiles set can_write = true where is_admin and not can_write;

create table if not exists contributor_invites (
  email text primary key check (email = lower(email) and email like '%@%'),
  note text, invited_by uuid references profiles on delete set null,
  created_at timestamptz not null default now(),
  accepted_at timestamptz, accepted_by uuid references profiles on delete set null
);
revoke all on contributor_invites from anon, authenticated;
alter table contributor_invites enable row level security;   -- 정책 0개 = 전면 거부

create or replace function may_write() ... security definer ...;

drop policy if exists posts_insert_own on posts;
create policy posts_insert_own on posts
  for insert with check (author_id = auth.uid() and may_write());
```

`can_write` 는 `is_admin` 과 마찬가지로 컬럼 GRANT 목록에서 빠져 있다 — 스스로 켤 수
있으면 초대제 전체가 장식이다. 자세한 것은 [RLS.md](./RLS.md).

권한 회수(`can_write = false`)는 새 글과 수정을 막지만 **삭제 정책은 일부러 손대지
않았다.** 남의 지면에 자기 글을 붙잡아 두는 쪽이 더 나쁘다.

### 앱

- `/write` 가 `ADMIN_PASSWORD` 자물쇠에서 **로그인 세션**으로 옮겨 갔다.
  `lib/adminGate.ts` · `components/PasswordGate.tsx` · `lib/adminPosts.ts` 삭제.
  환경변수 `ADMIN_PASSWORD` · `ADMIN_AUTHOR_ID` 도 사라졌다.
- `savePost` 가 `adminClient()`(service_role) 대신 `sessionClient()` 를 쓴다.
  `author_id` 를 환경변수가 아니라 세션에서 꺼내므로 **남의 이름으로 쓰는 경로가
  애초에 없고**, 소유권 판정이 RLS 한 곳에서만 일어난다.
- 화면 셋: `/u/[handle]` 필자 페이지(ISR 60초), `/me` 내 글 관리(초안·삭제),
  `/editor` 편집실(초대 · 권한).
- 홈 · 카드 · 상세의 필자명이 `/u/[handle]` 로 연결됐다.
- 초대는 **메일을 보내지 않는다.** 명단에 적어둘 뿐이고, 그 주소로 가입하는 순간
  `claimInvite` 가 권한을 켠다. 발송 경로를 하나 더 만들면 그때부터 스팸 신고와
  도메인 평판을 관리해야 하는데, 초대가 한 달에 몇 건인 단계에서 그 비용이 더 크다.

### 곁들여 고친 버그 — 좋아요가 글의 `updated_at` 을 밀고 있었다

`sync_like_count()` 가 `posts` 를 UPDATE 하고, 그 UPDATE 가 `posts_touch_updated_at` 을
깨운다. **아무도 글을 고치지 않았는데 좋아요 한 번에 `updated_at` 이 `now()` 로 밀렸다.**

지금까지는 `updated_at` 을 읽는 화면이 없어 조용했지만, `/me` 가 "마지막 수정" 을
보여주고 M3 에서 좋아요가 붙는 순간 눈에 보이는 오작동이 된다. RSS 갱신 · "수정됨" 표기 ·
sitemap lastmod 도 같은 값을 쓰게 된다.

카운터를 제외 목록으로 적는 대신 **사람이 고치는 칸을 허용 목록으로** 적었다.
카운터가 하나 더 늘어도 이 조건은 그대로 옳다.

```sql
create trigger posts_touch_updated_at
  before update on posts for each row
  when (old.title is distinct from new.title
     or old.deck is distinct from new.deck
     or old.body is distinct from new.body
     or old.category is distinct from new.category
     or old.status is distinct from new.status
     or old.thumbnail_url is distinct from new.thumbnail_url
     or old.thumbnail_ratio is distinct from new.thumbnail_ratio)
  execute function touch_updated_at();
```

## 2. M2-2 — 셋업 자동화 · 자동저장 · 툴바

### 셋업이 명령 두 줄이 됐다

이전에는 마이그레이션 넷을 SQL Editor 에 하나씩 붙여넣고, 대시보드에서 계정을 만들고,
UUID 를 복사해 `seed.sql` 을 고치고, 다시 실행해야 했다. 사람이
"몇 번까지 돌렸더라" 를 기억해야 하는 상태였고, 그건 기억으로 관리할 일이 아니다.

```bash
npm run db:migrate                        # 안 돌린 것만, 이름 순서대로
npm run db:admin -- me@example.com        # 계정 + profile + 편집장 권한
```

- `scripts/db-migrate.mjs` — 실행 이력을 DB 의 `schema_migrations` 에 남긴다. 파일
  하나가 통째로 한 트랜잭션이라 중간에 실패하면 그 파일은 아무것도 적용되지 않고,
  고친 뒤 다시 돌리면 남은 것부터 이어서 실행한다. `--dry` · `--redo <파일>` 지원.
  앞으로 `ALTER TYPE ... ADD VALUE` 같은 문장이 필요해지면 파일 첫 줄에
  `-- no-transaction` 을 적으면 된다.
- `scripts/db-admin.mjs` — 계정이 없으면 만들고, profile 이 없으면 만들고, 권한을 켠다.
  이미 다 돼 있으면 아무것도 바꾸지 않는다.

**`DATABASE_URL` 이 따로 필요한 이유:** service_role 키는 PostgREST 를 통과하므로
테이블만 다루고 DDL 은 못 돌린다. 이 값은 마이그레이션 실행기 전용이고 앱은 읽지 않는다 —
Vercel 에 넣을 필요도 없다.

**`db:admin` 이 따로 필요한 이유:** `is_admin` 은 애플리케이션 어디에서도 켤 수 없다.
앱에서 편집장을 만들 수 있으면 그 경로가 곧 권한 상승 경로다. 그래서 첫 편집장은 반드시
앱 바깥에서 만들어야 하고, 그 계정이 없으면 아무도 `/editor` 에 못 들어가 누구도
기고 권한을 받지 못한다.

### 자동저장

`PostEditor` 는 지금까지 그냥 `useState` 였다. 3천 자짜리 에세이를 쓰다 탭이 닫히면
통째로 사라진다. **긴 글을 받는 매체에서 이건 기능 부족이 아니라 결함이다** —
기고자가 한 번 겪으면 다시 쓰지 않는다.

두 겹으로 막았다 (`components/useAutosave.ts`).

| 겹 | 주기 | 조건 | 남는 곳 |
|---|---|---|---|
| 브라우저 | 0.6초 | 항상 | `localStorage` |
| 서버 | 3초 멈추면 | **초안일 때만** | `posts` |

새 글은 첫 자동저장에서 초안이 만들어지고 주소가 `/write/<id>` 로 바뀌므로
(`history.replaceState`) 새로고침해도 이어진다. 다시 들어오면
"저장되지 않은 내용이 있습니다 → 복구 / 버리기" 바가 뜬다.

**발행된 글은 서버 자동저장을 하지 않는다.** 지면에 나가 있는 글을 사람이 저장을
누르지도 않았는데 덮어쓰면 안 된다. 그 경우에도 브라우저 초안 복구는 그대로 돈다.

자동저장은 `revalidatePath` 를 부르지 않는다. 초안은 어느 캐시된 지면에도 나가지 않고,
몇 초마다 홈 캐시를 비우면 자동저장이 곧 사이트 성능 문제가 된다.

### 마크다운 툴바

굵게 · 기울임 · 소제목 · 인용 · 목록 · 링크 · 이미지 · 구분선. 여덟 개만 뒀다.
리치 에디터를 쓰지 않는다는 §6 M1 의 결정은 유지하되, 초대제로 외부 필자를 받기
시작한 이상 `##` 와 `![]()` 를 외우게 하는 건 다른 문제라 그 사이만 메웠다.

툴바가 textarea 를 직접 고치지 않고 `Edit` 을 돌려주는 이유: 본문은 React state 라
DOM 을 직접 쓰면 다음 렌더에서 되돌아가고, 커서 위치도 렌더 뒤에 잡아야 한다.

### 발행 즉시 반영

이미 되고 있었지만 `/me` 를 무효화 목록에 더했다. 서버 액션 안에서 `revalidatePath` 를
부르므로 브라우저의 라우터 캐시도 함께 비워진다 — 발행 직후 홈으로 돌아가도 옛 지면이
보이지 않는다.

```
/  ·  /category/<cat>  ·  /p/<id>  ·  /u/<handle>  ·  /feed.xml  ·  /me
```

### 편집실 열쇠 (임시)

매직링크 메일 왕복이 번거롭다는 요청. **"비밀번호를 맞히면 관리자 권한을 준다" 가
아니라 "비밀번호로 편집장 계정에 로그인한다" 로 만들었다.**

전자는 M2-1 이 막은 자가 승격 경로를 애플리케이션에 다시 뚫는 것이고, 그러면
`auth.uid()` 가 비어 글의 필자를 세션에서 꺼낼 수 없어 service_role 쓰기가 되살아난다.
후자는 진짜 세션을 만들기 때문에 **RLS · 초대제 · 컬럼 GRANT 가 전부 그대로 작동한다.**
사람이 겪는 절차는 같다 — 비밀번호 한 칸.

```bash
npm run db:admin -- me@example.com --password '정할비밀번호'
# .env.local
ADMIN_EMAIL=me@example.com
```

`ADMIN_EMAIL` 이 켜져 있을 때만 `/login` 에 "편집실 열쇠" 칸이 생기고, 지우면 화면과
서버 액션이 **함께** 닫힌다(화면만 감추면 액션은 살아 있어 아무나 직접 호출할 수 있다).
빌드할 때마다 켜져 있다고 경고한다.

**임시 통로다.** 열쇠가 새면 지면 전체가 넘어간다. 다른 사람을 초대해 각자 자기
계정으로 들어가기 시작하면 `ADMIN_EMAIL` 을 지울 것.

## 3. 검증

SQL 을 150줄 넘게 썼는데 한 번도 실행된 적이 없어서, 로컬 Postgres 16 에 Supabase
객체(`auth.users` · `auth.uid()` · `anon`/`authenticated`/`service_role` 롤 ·
기본 권한)를 흉내 낸 shim 을 얹고 실제로 돌렸다.

- 마이그레이션 **4/4 실행 성공**, 재실행 시 건너뜀, `--redo` 동작
- `check_rls.sql` **19개 항목 전부 PASS**
- 행 단위 동작 확인
  - 초대받은 사람 글쓰기 ✅
  - 초대 없이 글쓰기 차단 ✅ (`insufficient_privilege`)
  - 스스로 `can_write` 켜기 차단 ✅ (컬럼 GRANT)
  - 권한 회수 후 자기 글 수정 차단 ✅ / 삭제는 허용 ✅ (의도한 동작)
  - 로그인 사용자의 초대 명단 읽기 차단 ✅
  - 좋아요 · 댓글이 `updated_at` 을 밀지 않음 ✅, 본문 수정 시에는 움직임 ✅
  - 좋아요 취소도 카운터만 건드림 ✅

`npm run typecheck` 통과, `next build` 컴파일 통과.
(prerender 는 실제 Supabase 프로젝트가 있어야 하므로 이 환경에서는 확인 못 함.)

## 4. 남은 것

### 지금 막고 있는 것

- **이미지 업로드가 없다.** 툴바의 "이미지" 는 `![](https://)` 를 넣어줄 뿐 주소는 사람이
  채워야 한다. 초대제로 외부 필자를 모셔놓고 "이미지는 알아서 어딘가 올리고 URL 주세요"
  라고 하는 상태다. Supabase Storage 작업이고 `next/image` 전환까지 묶여 있다(§8 미결정).
  **외부 필자가 실제로 글을 보내기 시작하면 여기서 제일 먼저 막힌다.**
- **미리보기가 실제 지면과 다르다.** `PostEditor.module.css` 의 `.preview` 와
  `app/p/[id]/page.module.css` 의 `.body` 가 서로 다른 스타일이다. 2b 는 활자 위계가
  디자인의 전부라, 미리보기에서 멀쩡하던 글이 발행하면 다르게 보인다.

### 운영

- `ADMIN_EMAIL` 지우기 — 다른 사람을 초대하고 나면
- **`npm run test:rls` 를 실제 Supabase 프로젝트에서 한 번도 돌리지 않았다** —
  M2 완료 기준
- 이용약관 8조(게시물 관리) · 9조(권리 귀속) 채우기 — 남의 글을 받는 매체에서
  비어 있으면 안 되는 조항
- Vercel 연결, 제호 확정, 발행 대기 원고

### M3 전에 결정할 것

- `likes_read_all` 이 `using (true)` 라 **누가 무엇에 좋아요했는지 전부 공개된다.**
  개수는 `posts.like_count` 에 있으므로 select 를 본인 행으로 좁힐 것.
- 비로그인 좋아요의 `actor_key` — 쿠키 UUID 는 시크릿 창으로 무한, IP 해시는 개인정보와
  NAT 문제. 초대제를 고른 이 지면이라면 "좋아요도 로그인 사용자만" 이 일관된다.
- `/editor` 명단 200명 상한 — 넘으면 검색 필요
- 권한을 회수해도 발행글은 남는다. 내리려면 `status = 'hidden'` 인데 그 UI 가 없다.
